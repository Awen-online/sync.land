OBS Player — Architecture & Data Flow

How the dock (frontend) and the streamer API (backend) fit together to license, stream, and audit music playback during a live broadcast.

Frontend repo: Awen-online/syncland-obs-player Backend mu-plugin: syncland-streamer-api.php
TL;DR
The Sync.Land OBS Player is two components working together: a dock — the frontend SPA loaded as a browser panel inside OBS Studio — and a streamer API — the PAT-authenticated backend that hands it playlists, per-track license clearance, and stream URLs. The dock is what the streamer sees. The streamer API is what makes it work. Both live under one system called Sync.Land OBS Player.

1 · The two halves at a glance

The dock Frontend

A static Vite-built single-page app. Runs in the browser context that OBS Studio embeds in its Custom Browser Dock panel.

Hosted at sync.land/dock/. Holds no secrets. Receives a Personal Access Token (PAT) from the streamer, stashes it in localStorage, and Bearer-auths every backend call. Ships from Awen-online/syncland-obs-player under Apache 2.0.

The streamer API Backend

A REST API namespace at /wp-json/FML/v1/streamer/*, implemented as the syncland-streamer-api.php mu-plugin on the Sync.Land WordPress node.

Validates the PAT against wp_streamer_tokens, resolves the caller to a WordPress user, and returns only that user’s playlists / their songs’ SLFS-v1 clearance. Every response is CORS-open because the PAT is the security boundary, not the origin.

2 · Glossary — two words with two meanings

Both of the words in the project name overload two concepts. Worth pinning explicitly so nothing gets confused later.

Dock
1. OBS Studio’s built-in Custom Browser Dock — a panel type inside OBS that loads any URL you give it. Any OBS user can add one.
2. The Sync.Land Dock SPA — the frontend web app at sync.land/dock/ that a streamer loads into that OBS panel. This project’s frontend.
Streamer
1. The person broadcasting on Twitch or YouTube Live — the end user of this system.
2. The /streamer/* REST API namespace on Sync.Land — the backend endpoints that serve the dock. Named after who they’re for.
PAT
Personal Access Token. Format sk_syncland_<40 chars>, 53 chars total. Server stores SHA-256 hex only; plaintext shown exactly once at creation. Bearer credential for every dock→API call.
SLFS-v1
Sync.Land Free Sync License, version SLFS-v1.0-2026-07-11. The tier that permits creator-scale live-stream use with attribution. Every track played through the dock is deemed licensed under it.
Attribution overlay
When the dock is loaded as an OBS Browser Source (not a dock), it strips its UI to just the current attribution string — e.g. Music: Cullah — via Sync.Land — sync.land/song/parietals. The streamer places this on-scene so the on-air attribution meets SLFS-v1 §6.

4 · Data flow — provisioning a token

One-time, out-of-band. Happens once per streamer, in the browser at sync.land/account/tokens/. The dock never sees this flow — it starts with a PAT already in hand.

sequenceDiagram
    autonumber
    participant U as Streamer
    participant W as sync.land
/account/tokens/
    participant DB as wp_streamer_tokens
    U->>W: Sign in, click "Generate token"
    W->>W: random_bytes(30)
prefix "sk_syncland_"
    W->>DB: INSERT SHA-256(token), prefix, name, user_id
    W-->>U: Plaintext PAT (shown once)
    Note over U: Streamer copies PAT
and pastes into the dock

The server never stores or retransmits the plaintext PAT. If lost, the streamer generates a new one; if compromised, the streamer revokes it by id or prefix.

Every track is license-checked immediately before playback. A track that fails the check is skipped, never played — so a paused or removed track can never end up on-air.

6 · API surface

All endpoints live under /wp-json/FML/v1/streamer/*. The dock talks only to the top four; the bottom three exist for the same-origin /account/tokens/ page that mints and revokes tokens.

Method Endpoint Auth Purpose
GET /streamer/me PAT Sanity-check the token, return caller identity.
GET /streamer/playlists PAT List the streamer’s playlists with track lists, cover art, and per-track duration.
GET /streamer/track/{id}/clearance PAT Per-track license check + stream URL + attribution text + album + duration + cover.
POST /streamer/track/{id}/played PAT Log a play event to the analytics audit trail (fire-and-forget).
GET /streamer/tokens WP nonce List existing PATs (same-origin, for the account UI).
POST /streamer/tokens WP nonce Create a new PAT.
DELETE /streamer/tokens/{id} WP nonce Revoke a PAT.

7 · Security model

  • PATs are stored server-side as SHA-256 hex only. The plaintext is shown exactly once at creation, then unrecoverable.
  • Every PAT row carries a public 16-char prefix (sk_syncland_abcd) so the streamer can identify and revoke a specific one without seeing the whole token again.
  • /streamer/* responses reflect the caller Origin via Access-Control-Allow-Origin. That’s safe because the PAT is the security boundary — origin restriction adds no real defense against an attacker who holds a valid token, but it does block legitimate self-hosted dock mirrors.
  • The SPA holds the PAT only in browser localStorage, scoped to the dock’s origin. It is never posted to any endpoint except the Sync.Land API. Revoking a token invalidates it server-side even if the browser still has it.
  • Token-management endpoints (/streamer/tokens) are same-origin only (WP nonce auth). A stolen PAT cannot mint or revoke other PATs — only the account UI running under a live sync.land session can.
  • No session cookies, no server-side per-request state, no OAuth complexity. v0.2 will add OAuth2/PKCE as an alternative for streamers who prefer not to handle tokens directly.

External application verifies a sync license via public API Every GET /streamer/track/{id}/clearance call is exactly this — a fully external OBS instance receives a machine-readable SLFS-v1 clearance response with tier, attribution text, and stream URL. The dock demonstrates it end-to-end on air.
